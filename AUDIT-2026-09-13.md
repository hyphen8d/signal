## HIGH

### H1 · A failed audition search renders on the dashboard as a clean, empty result

`tools/network.html` `renderAuditionResult()` (~line 1027) never reads
`searchFailures` — the file does not contain the word. The run-level banner
reads only `unverified`.

Before today `audition.js` exited 2 with no JSON on a failed search, and the
panel said "no structured result — see the log". Today's reliability pass made
it exit 1 **with** valid JSON: `rows: []` plus `searchFailures`. The dashboard
sends one search per run, so one failure is every failure, and the panel now
shows the constraints box over an empty grid and no message. The exit code is
never shown; only the red streamed log says anything. The CHANGELOG entry says
the failures appear "in the `--json` summary the dashboard renders" — the
server sends them, the page drops them.

Reproduced: `admin-server.mjs` with `fetch` stubbed offline, POST
`/api/audition` `{"stationId":"after-hours","searches":["Miles Davis Blue in
Green"]}` → `RESULT parsed: true … rows: 0 searchFailures: [{…"fetch
failed"}]`, `exit 1`. Old tree: `exit 2`, 0 bytes of stdout.

**Fix:** a banner beside the unverified one when `searchFailures?.length`;
"no candidates" when `rows` is empty.

### M2 · [S] or [P] during a cross-band secret preset strands the dial on the wrong band (older code, 2026-09-12 H6)

`program.js` `presetTune()` (~2770, ~2820) switches band before the sweep
starts. `[S]` mid-sweep only calls `stopScan()` (because `scanning` is true);
`[P]` clears the timer. Reproduced: boot AFTER HOURS, power on, `0`, `s` at
+50ms → `band=ym freq=1200 mode=seeking`. The screen shows the YM scale
`100.0 … 900.0` with readout `1200.0` and `[ TUNING... ]` stuck; `[P]` gives the
same, it survives a power cycle, and the next arrow wraps to 100.

**Fix:** clamp `freq` into the current band and retune when a preset sweep is
cut short — or commit the band only when the lock lands.
